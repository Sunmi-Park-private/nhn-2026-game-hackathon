### 1-2. 공통 원칙 — 사람이 정하고, AI가 만들고, 사람이 검증한다

```
① 사람  기준 정의 ──기준──▶ ② AI  생성 ──산출물──▶ ③ 사람  검증·선별
                              ▲                          │
                              └────── 반려 → 기준 안에서 다시 ──┘
```

| 단계 | 개발 | 디자인 |
|---|---|---|
| ① 기준 | `docs/GDD.md` · 스펙 · `CLAUDE.md` 규약 5조 | `docs/ART_SPEC.md` (규격·비율·슬롯 경로) |
| ② 생성 | Task 단위 구현 diff | 복수 시안 |
| ③ 검증 | 타입체크 · 테스트 · 화면 확인 · 코드 리뷰 | 에디터에 올려 실기 확인 · 선별 |

③에서 나가는 경로는 승인과 반려 둘뿐이고 둘 다 사람이 고른다. **AI가 스스로 산출물을 확정하는 지점은 없다.** 코드는 PR 머지로, 아트는 에디터 업로드로만 게임에 들어간다.

## 02. 사람과 AI의 역할 분담

「게임을 만들어줘」라고 맡기지 않았다. 흐름은 항상 같다:

```
GDD(기획) → 스펙(실측·재사용 판정·모듈 분해) → 플랜(Task 단위) → Task별 서브에이전트 구현 → 리뷰 → PR
```

| 사람 | AI |
|---|---|
| 주제 해석 · 규칙 결정 · 결정 근거 기록 | 코드베이스 실측 (파일·줄 번호) |
| 스펙 승인 (Director 확정 표) | 스펙·플랜 초안 작성 |
| Task 경계 · 병렬 여부 결정 | Task 구현 · 테스트 작성 |
| 검증 결과 판독 · 승인 또는 반려 | 검증 게이트 실행 (tsc · vitest) |
| 커밋 · 푸시 · PR 머지 승인 | 커밋 메시지 · PR 본문 생성 |

### 왜 이렇게 했나

- **잘못된 전제 위에 쌓인 구현은 통째로 버려야 한다.** 그래서 스펙은 실측으로 시작하고, 근거가 사라지면 판단을 뒤집는다.
- **검증 없는 「완료」 보고는 신뢰할 수 없다.** 그래서 명령 출력을 근거로 내게 했다(§3-2).
- **여러 세션이 동시에 작업하면 서로의 변경을 덮어쓴다.** 그래서 worktree로 격리했다(§3-3).

## 03. 개발 AI 대상 주요 프롬프트 및 지시 사항

실제로 사용한 지시문이다. 전부 저장소에 그대로 남아 있다.

### 3-1. 프로젝트 규약 — `CLAUDE.md`

모든 세션이 시작할 때 읽는 문서. **낡지 않는 것만 적고, 빨리 어긋나는 값은 재는 명령을 적는다**는 원칙으로 썼다.

```
data (JSON · 상수) → engine (순수 TS) → ui (Pixi 렌더)
의존은 한 방향으로만 흐른다. engine/이 렌더러를 모르기 때문에 테스트가 헤드리스로 돈다.
grep -rn "pixi.js" src/engine | wc -l   # 0이어야 한다
```

코드 규약 5조 — 새로 쓰는 코드에만 적용하고 기존 부채는 상환하지 않는다:

```
1. 새 파일은 200줄에서 자른다            — 병렬 작업의 상한이 된다
2. 새 ui/ 파일은 ../data를 직접 import하지 않는다 — 한 기능에 접점 하나
3. 새 JSON은 as unknown as로 받지 않는다   — 필드별 검증, 어긋나면 기본값
4. 화면 전환 상태를 모듈 전역 let으로 두지 않는다 — 클로저 안 객체 하나
5. 치트·디버그는 devMode 게이트 뒤에만
```

각 조에 **현재 코드의 근거와 다시 재는 명령**을 붙였다. 근거가 사라지면 그 조도 다시 판단한다.

### 3-2. 검증 게이트 — 완료를 주장하기 전에

```
npm run build    # tsc --noEmit + vite build
npm test         # vitest
```

플랜의 Global Constraints에 기준선을 박아 둔다:

```
- 기존 테스트는 하나도 깨지지 않아야 한다. 기준선: npm test → 207 passed / 15 files.
- engine/race/는 pixi.js를 import하지 않는다. 검증: grep -rn "pixi.js" src/engine | wc -l → 0
```
— `docs/superpowers/plans/2026-09-05-animal-race.md` Global Constraints

말로만 「완료했습니다」라고 하지 못하도록 **명령 출력을 근거로 제시**하게 했다.

### 3-3. 동시 작업 규약 — worktree + PR

```
모든 작업은 git worktree로 분리한 별도 브랜치에서 하고, PR 단위로 push → 머지한다.
베이스는 main. 각 worktree는 node_modules를 공유하지 않으므로 npm install이 따로 필요하다.
```

```
git commit -a를 쓰지 않는다. 항상 경로를 명시해 스테이징한다.
커밋 전에 git status --short와, 공유되는 JSON(uiLayout.json, assets.json)은 git diff를 반드시 본다.
```
— 실제로 다른 세션의 미커밋 작업을 커밋이 삼킨 사고 뒤에 추가한 규약

```
브랜치 CI 통과는 머지 결과의 통과가 아니다. 머지 전 최신 main 위에서 다시 검증한다.
```

### 3-4. 서브에이전트 브리프에 매번 넣은 것

```
- 이 워킹트리는 공유 자원이다. 경로를 명시해 스테이징하고 자기 hunk만 골라 담는다.
- 이 테스트는 내가 썼고 아무도 안 봤다 — 충실도가 아니라 코드 자체를 보라.
- 테스트를 쓸 때마다 「production 코드가 틀렸다면 이 단언이 실패하는가」를 묻는다.
```

### 3-5. 시간 압박 규약 — `CLAUDE.md` 「시간이 없을 때」

```
코드 동결은 09-06 03:00이다. 미완 기능은 고치지 말고 뺀다.
자르는 순서: 연출 → 메타(레이스·도감) → 코어. 코어를 마지막까지 지킨다.
새 메커닉을 넣을 때: 코어가 그 기능을 import하지 않는다 · 진입점을 한 곳에 묶는다 · 공유 상태는 최소로
```

## 05. 자동 판정 — 디자이너 오투입을 테스트가 잡는다

AI가 만든 코드가 **사람의 실수를 미리 잡는 자리**로 쓰였다.

| 테스트 | 잡는 것 |
|---|---|
| `tests/hex/tileArtSize.test.ts` | 타일 아트 캔버스 여백. 여백이 있으면 육각이 칸의 80%만 채워 판에 틈이 생긴다 |
| `tests/hex/assetManifest.test.ts` | 매니페스트 슬롯이 실제 파일을 가리키는지 |
| `tests/ui/uiLayoutDiff.test.ts` | 두 에디터가 같은 배치 파일을 덮어쓰지 않는지 |
| `engine/hex/stageLoader.ts` | 스테이지 JSON 형태가 틀려도 기본값으로 뜬다 |

```
처음 받은 아트가 512×512 정사각 캔버스에 409×470 육각이라 육각이 칸의 79.9%만 채웠고,
판 전체에 20%짜리 틈이 보였다. tests/hex/tileArtSize.test.ts가 이 규격을 검사한다.
```
— `docs/ART_SPEC.md` §2

재는 명령: `find tests src -name "*.test.ts" | wc -l` · `npm test`

## 07. 규격이 곧 프롬프트다 — `ART_SPEC.md`

디자이너에게 넘긴 사양 자체가 생성 기준이 되게 썼다. 「예쁘게」가 아니라 **게임에 들어갈 수 있는 조건**을 숫자로 적었다.

```
| 육각형 방향 | pointy-top |
| 가로:세로 비율 | √3 : 2 ≈ 0.866 : 1 |
| 캔버스 여백 | 0 — 캔버스가 곧 육각의 바운딩 박스다 |
```

```
전체는 16:9 가로, 게임은 중앙 9:16 세로 컬럼 안에서만 논다.
검산: 9/16 + 2×(175/288) = 16/9. 오차 0의 정확한 분할이다.
게임에 필요한 것은 하나도 좌우 패널에 두지 말 것.
```

### 7-1. 일관성 — 6종이 한 세트로 보여야 한다

- 6색 타일: 파장 순서 고정. 색만 다르고 형태·아웃라인·광택은 같다
- 동물 6종: 창살 2장 · 구출 시퀀스 · 달리기 시퀀스 · 도감 카드 2장 · 로비 친구 1장이 **같은 id**로 묶인다 (`data/animals.ts` 단일 출처)
- 한 종을 늘리면 위 전부가 동시에 필요하다 → **종 수를 6으로 잠갔다** (펭귄 제외 결정, GDD §7)

## 10. 게임 적용 최적화와 자산 관리

- **화면 규격**: 논리 450×800, 전체 16:9 안의 중앙 9:16. 좌우 패널은 장식 전용
- **포맷**: 이미지는 업로드 시 WebP 자동 변환. 영상은 mp4(H.264) 또는 webm
- **로딩**: 인트로 영상 → 로딩 화면(여기서 에셋 로드 시작) → 로비. **인트로와 로드를 겹치지 않는다** — 겹치면 실제 빌드에서 영상이 버벅였다
- **캐시**: 캐시 버스터가 캐시를 매번 무력화하고 있던 것을 발견해 뗐다 — 터널에서 9초 → 3초
- **버전**: 슬롯 기반 매니페스트(`src/data/assets.json`)에 파일 단위로 기록. 코드 수정 없이 아트 교체

## 12. AI 활용의 한계와 사람의 개입

정직하게 적는다. AI가 전부 해낸 것은 아니다.

### 12-1. AI가 잘한 것

| 영역 | 내용 |
|---|---|
| 개발 | **실측** — 파일·줄 번호를 읽어 설계 근거로 만드는 일. 반복 작업 — 슬롯 배선, 매니페스트, 테스트 골격. 회귀 검증 |
| 디자인 | 대량 생성 — 6종 × 상태별 세트를 한 스타일로 |

### 12-2. 사람이 개입해야 했던 것

- **규칙 결정** — 「발사체는 항상 빨강」이 구출을 불가능하게 만든다는 것은 **실제 플레이에서** 발견했다. AI는 규칙을 구현했지 규칙이 틀렸다고 말하지 않았다 (GDD §5-2)
- **재미 판단** — 샷 리밋만으로는 재미의 축이 하나라는 것. 천장 하강으로 바꾼 결정 (GDD §5-8)
- **잘라내기** — 펭귄 제외, 월드 화면 진입점 제거, 미션·상점 미구현. 무엇을 안 만들지는 사람이 정했다
- **아트 판단** — 어느 시안이 「이 게임의 것」인지
- **검증 설계의 결함** — 발사대 작업(PR #7)에서 리뷰가 잡은 결함 다섯 중 **넷이 구현이 아니라 AI가 쓴 테스트**였다. 절대 실패할 수 없는 단언, 물리가 아니라 격자를 재는 대칭 테스트. **구현보다 「무엇으로 맞다고 할 것인가」가 약한 고리**였다
- **동시성 사고** — 공유 워킹트리에서 다른 세션의 작업을 커밋이 삼킨 일. 이후 규약(§3-3)을 사람이 추가했다
- **실기 성능** — 인트로 영상 중 백그라운드 로딩이 실제 빌드에서 버벅인다는 것은 사람이 기기에서 봤다

### 12-3. 도메인 지식이 필요한 이유

AI가 생성을 대신해준 만큼, **무엇을 요구할지 아는 능력**의 비중이 커졌다.

- 육각 격자의 pointy-top · 여백 0 · √3:2를 모르면, 예쁘지만 판에 틈이 생기는 타일이 나온다
- 앵커 · 부유 클러스터 · flood fill 같은 개념을 모르면 스펙을 Task 단위로 쪼갤 수 없다
- 「단언이 실제로 실패하는가」를 묻지 않으면 AI가 낸 「테스트 통과」를 검증할 방법이 없다

**AI는 실행을 압축했지만 기준을 대신 세워주지는 않았다.** 어디서 사람이 개입해야 하는지를 알고 설계하는 것이 이 프로젝트에서 확인한 생성 AI 실무의 핵심이었다.
